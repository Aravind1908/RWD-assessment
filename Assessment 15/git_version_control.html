What is Version Control?

Why every project needs a record of its changes, why Git became the default, and what "distributed" actually means — with two demos that run on one machine.

Version Control · Git · DVCS vs CVCS

1Introduction

Version control is a system that records changes to files over time so you can retrieve any earlier state. Every save point — called a commit — is a snapshot of the project, tagged with who made it, when, and why (a message). Without version control, "the last version" is a folder named final_FINAL_v3_really.

Git (2005, created by Linus Torvalds for the Linux kernel) became the industry standard for four practical reasons:

  • Speed — commit, log, branch and diff run entirely on your machine in milliseconds.
  • Offline work — a Git clone is a complete repository; the network is optional.
  • Every clone is a backup — the project's full history exists in as many places as there are developers.
  • Cheap branching — trying an idea is a one-command, near-zero-cost operation, so teams branch constantly instead of fearing it.
# what a version-controlled project "remembers"
c3f9a12  "fix login timeout"        Priya   2026-09-18 14:02
a1b2c3d  "add retry to payments"    Dev   2026-09-17 11:40
7e2f0b1  "first version"            Dev   2026-09-15 09:12
# any one of these snapshots can be restored at any time

VCS tools split into two families — centralized (SVN, Perforce, TFVC) and distributed (Git, Mercurial) — and the difference is a single architectural decision: where the full history lives.

2Syntax and its Explanation

The core idea: commits are snapshots

A commit is a snapshot of the whole project (Git records what each file contained, not a list of edits), identified by a content-based hash — a1b2c3d is a commit, and it doubles as a bookmark, an address and a fingerprint. Because the hash is computed from the content, you cannot silently alter history: any change produces a different hash.

Centralized VCS (CVCS) — one server is the truth

In a centralized model, a single server holds the repository. Clients check out working copies, and nearly every operation — committing, reading old logs, comparing versions — requires a connection to that server. 

client A ─┐
client B ─┼──>  CENTRAL SERVER  (the only copy of the full history)
client C ─┘

Examples: Subversion (SVN), Perforce, Team Foundation Version Control. Consequences: fastest possible setup and one canonical location, but a single point of failure — server down, and nobody can commit, read history, or diff old versions.

Distributed VCS (DVCS) — every clone is the truth

In a distributed model, clone copies the entire repository — full history, all branches — to your machine. Commits, logs, branches and diffs are local operations that never touch the network. Remotes exist purely to sync clones with each other. 

your clone (full copy)  ──push/pull──>  "origin" (just another clone,
   + your local commits,            typically on GitHub/GitLab — a
     branches, history                  convenience, not a dependency)

Examples: Git, Mercurial. Consequences: offline capability, many independent copies (a clone is a backup), and arbitrary topologies — any clone can serve as the "server", and teams push/pull peer-to-peer, not just to a hub.

GitHub is not the point. Git doesn't need GitHub. "origin" is the name of a sync partner — a bare repository on a server, a USB stick, or a teammate's laptop. The centralized habit of treating the server as the project is exactly what the distributed model removes.

3Features & Uses

What teams actually use it for

  • Undoing mistakes — restore any file from any commit; the "oops" is a command, not a catastrophe.
  • Answering "who changed what, when, why" — git log, git blame turn arguments into lookups.
  • Parallel work — each developer (or feature) works on its own branch; merge when ready.
  • Experiments without risk — a branch you abandon costs nothing.
  • History as documentation — commit messages + reviews form a narrative of how the code evolved.
  • Releases and rollbacks — tag a commit as v2.1, and you can always go back to it exactly.

Same incident, two worlds

6 pm: you need to commit; the network/server is downWhat happens
CVCSYou're blocked. The only copy of the history is unreachable; even reading yesterday's log may fail.
DVCS (Git)You commit, branch and diff normally — everything is local. You push tomorrow; nobody notices.
Why version control, in one line: it is the safety net that makes collaboration possible — it turns "whose copy is the right one?" into a question with a definite, provable answer.

4Example Programs with Explanation

Both examples are terminal scripts — they build a throwaway repository in a temp folder, print what's happening, and clean up after themselves. They need Git installed and nothing else.

Example 1 — Why VCS exists: undo a mistake, read the history

A file gets broken. Version control gives it back and remembers every state in between.

#!/usr/bin/env bash
set -euo pipefail
demo=$(mktemp -d)/undo-demo && mkdir -p "$demo" && cd "$demo"

git init -q                          # start tracking this folder
git config user.email "[email protected]"
git config user.name  "You"
echo "v1 of the app" > app.txt
git add app.txt
git commit -qm "first version"       # snapshot 1 saved

echo "oops, broke it" > app.txt      # simulate a bad edit
git status --short                   # M  app.txt — git knows it changed
git restore app.txt                  # undo: file is back to the committed state
cat app.txt                          # "v1 of the app" — the damage is gone

git log --oneline                    # the history, newest first
git log --stat --oneline             # …with what each commit touched
Explanation of Example 1:
  • git init turns an ordinary folder into a version-controlled one — from then on, Git watches what you save.
  • git commit is the save point: a named snapshot that survives any later damage.
  • git status is the "what changed?" check — here it reports M app.txt (modified, not yet saved into a commit).
  • git restore throws away the bad edit and brings the file back to the last committed state — the everyday "undo" that no folder named backup can give you.
How to run
Save as example1_vcs_undo_history.sh and run bash example1_vcs_undo_history.sh — or paste the lines into a terminal in any empty folder. You'll see the broken file heal itself and the history print out.

Example 2 — Distributed vs centralized, on one machine

A bare Git repository plays the role of "the central server". Watch what happens when it goes away — the difference between the two models in one experiment.

#!/usr/bin/env bash
set -euo pipefail
root=$(mktemp -d) && cd "$root"

# 1) a bare repo plays "the central server"
git init -q --bare server.git
git clone -q server.git work         # your clone: a FULL copy
cd work
git config user.email "[email protected]"
git config user.name  "You"
echo "line one" > notes.txt
git add notes.txt
git commit -qm "first commit"

# 2) "the server goes down" — rename the bare repo away
cd "$root" && mv server.git server.git-down
cd work
echo "line two" >> notes.txt
git add notes.txt
git commit -qm "commits still work — the full history is local"
git log --oneline                     # both commits, read entirely offline

# 3) "the server is back" — push the two commits
cd "$root" && mv server.git-down server.git
cd work
git push -q origin main 2>/dev/null || git push -q origin master
echo "done — the clone kept working without the 'server'"
Explanation of Example 2:
  • The clone in step 1 copied a complete repository — history, branches, everything — not just current files.
  • In step 2 the "server" no longer exists, yet committing and reading the log work perfectly. In a centralized VCS this is the step where the team stops.
  • In step 3 push simply synchronizes the two copies — the "server" received two commits it never saw happen. In a DVCS, origin is a peer, not a gatekeeper.
  • Run it twice and compare: the second run's push says Everything up-to-date — sync is idempotent and cheap.
How to run
Save as example2_distributed_vs_centralized.sh and run bash example2_distributed_vs_centralized.sh. Needs Git; uses only a temp folder.

5Advantages

  • Local-first speed: the operations you use a hundred times a day (commit, log, diff, branch) never touch the network.
  • Offline capability: planes, trains, flaky offices — work and commit continue; sync is a separate, later step.
  • Every clone is a backup: the full history exists in N places; losing one machine (or even the "main" server) loses nothing.
  • Integrity by design: content-addressed commits mean history can't be quietly corrupted or altered — a different hash is proof of a different state.
  • Branching is a non-event: near-zero cost makes feature branches, experiments and hotfixes the normal way of working instead of a risky escalation.
  • Arbitrary topologies: hub-and-spoke, peer-to-peer, or both — the model doesn't care who pushes to whom.
  • Industry gravity: GitHub/GitLab/Bitbucket, CI/CD pipelines and code-review flows are built around Git, so the skill compounds.

6Conclusion

Version control is the record of a project's changes — snapshots tagged with who, when and why. Git won because it made that record local, fast and everywhere: every clone carries the full history, so the network becomes optional and every machine becomes a backup.

The architectural difference in one sentence: in a centralized system the server is the project; in a distributed system every clone is the project. Centralized VCS (SVN-style) is a hub that the whole team depends on; distributed VCS (Git) is a mesh of complete copies that sync when convenient. Origin is a convenience, not a dependency.
