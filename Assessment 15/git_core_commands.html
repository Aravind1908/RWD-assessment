Git: Core Commands & the Three States

init, add, commit, status, log, diff — and the working directory → staging area → repository model that makes all six make sense. Two runnable terminal demos.

Version Control · Git · Fundamentals

1Introduction

Every Git file exists in one of three places at a time: the working directory (the files you actually edit), the staging area (a holding pen for "what the next commit will contain"), and the repository (the saved snapshots). The six core commands are just verbs that move a file through those places: 

working directory ──git add──> staging area ──git commit──> repository
        ↑                             │
        └────── git restore / reset ──┘   (backwards also exists)
CommandIn one line
git initstart tracking this folder (create the repository)
git statuswhere is everything right now?
git addput this change into the staging area
git commitsave the staged snapshot into the repository
git logwhat has been saved, in order
git diffwhat changed — between which two places

Learn the model and the commands stop being memorized: status tells you which area you're looking at, add and commit move files between areas, and diff shows the gap between any two.

2Syntax and its Explanation

git init — start a repository

git init            # in an existing folder
git init my-project # create the folder too

Creates a hidden .git directory holding the whole repository (objects, refs, config). After the first commit, the repo has a history; before it, it's an empty repository. Running init in an already-initialized folder is harmless — it just resets nothing and says so.

git status — the first command to type

git status          # human format
git status --short  # two-letter codes, one line per file

Reports three zones at once: staged (what will be committed), modified-but-unstaged (edits not yet staged), and untracked (files Git has never seen). If you only build one Git habit, make it status before add, diff before commit.

git add — move changes into the staging area

git add file.txt    # one file
git add .           # everything in this folder (and below)
git add -A          # everything, including deletions, from here up

add copies the file's current contents into the index (the staging area). You can add the same file twice — the second call just replaces the staged copy with the newer one. This is also how you stage part of a file: git add -p walks hunk by hunk.

git commit — save the staged snapshot

git commit -m "add retry logic to payment flow"
git commit -am  "fix typo"   # -a stages tracked-file edits first, then commits

A commit takes exactly what is staged and saves it as a new snapshot with a message, an author, a timestamp and a pointer to its parent commit. Nothing unstaged goes in — that's a feature (you can commit half your work) and the classic source of surprises (you committed nothing). The message is the commit's documentation: write it in the present tense, for future you.

git log — read the history

git log                 # full history, oldest last
git log --oneline       # one line per commit
git log --stat --oneline
git log -5              # last 5 commits
git log --author=Dev    # by a person

The repository as a timeline. Each entry shows the hash (the address), the message and the author — and every hash is a bookmark you can restore, inspect or branch from.

git diff — what changed where (the subtle one)

git diff             # working directory  vs  staging area
git diff --cached     # staging area      vs  last commit  (what WILL be committed)
git diff HEAD         # working directory vs  last commit  (everything combined)
git diff abc123 def456 # two commits against each other

diff always answers "how do X and Y differ?" — and the pairs depend on where you stand. Bare diff compares your files against what's staged; --cached compares the staging area against the last commit. Memorize those two and the rest are variations.

Which diff for which question

QuestionCommand
What have I edited that I haven't staged yet?git diff
What exactly will the next commit contain?git diff --cached
How does my whole tree differ from the last commit?git diff HEAD
What did commit A change compared to B?git diff A B
Going backwards (the modern split): git restore file.txt throws away edits in the working directory (back to the staged state); git restore --staged file.txt un-stages (back to the unstaged state). Older guides call both git reset — which still works for un-staging.

3Features & Uses

The three states, in one file's life

  1. Working directory. You edit notes.txt. Git sees it as untracked (never added), then modified (changed since the last commit). It exists only on your disk — one crash or one wrong save away from gone.
  2. Staging area (the index). git add copies the file's current contents into the index. This is Git's "pre-flight check": a deliberate, reviewable declaration of what the next commit will be — and the only place you can stage part of a file.
  3. Repository. git commit snapshots the index into an immutable, hash-addressed commit. From here the change is part of history: listable in git log, restorable anytime, shareable via push.
# git status — all three zones in one look
Changes to be committed:            ┌ staging area (will be committed)
  modified:   src/auth.js           │
                                      └
Changes not staged for commit:      ┌ working directory (edited, not staged)
  modified:   src/util.js           └

Untracked files:
  scratch/                          (git has never seen it)

Why the staging area exists

A commit is a story: "this change does one thing." The staging area is where you build that story — half your edits in, the other half left out, a partial file staged hunk by hunk (git add -p). Teams that skip it end up with commits like "misc"; teams that use it produce history they can actually read.

The daily loop, six verbs: status → diff → add → diff --cached → commit → log. That's 95% of a Git day.

4Example Programs with Explanation

Both are terminal scripts that build a throwaway repo in a temp folder and print each step as it happens. Git is the only requirement.

Example 1 — The three states in one session

One file makes the full journey: untracked → modified → staged → committed. status narrates every stop.

#!/usr/bin/env bash
set -euo pipefail
demo=$(mktemp -d)/three-states && mkdir -p "$demo" && cd "$demo"

git init -q
git config user.email "you@example.com"
git config user.name  "You"

echo "== 1) working directory: an untracked file appears =="
echo "hello v1" > notes.txt
git status --short                    # ?? notes.txt

echo "== 2) stage it, then edit it again =="
git add notes.txt
git status --short                    # A  notes.txt  (staged)
echo "extra line" >> notes.txt
git status --short                    # AM notes.txt  (staged + new unstaged edit)
git diff --cached                     # what the next commit WILL contain
git diff                              # the edit made after staging

echo "== 3) commit: the snapshot enters the repository =="
git add notes.txt
git commit -qm "first snapshot"
git status --short                    # (nothing — clean)

echo "== 4) history: what the repository remembers =="
git log --oneline --stat
echo "done — working dir -> staging -> repository"
Explanation of Example 1:
  • ?? notes.txt — untracked: the file exists only in the working directory, in no other area.
  • A notes.txt — added: its contents now sit in the staging area, waiting to be committed.
  • AM notes.txt — the interesting state: Added/staged, then Modified again. Two diff commands show the two halves side by side — exactly what the staging area is for.
  • After commit, status is empty and log shows the snapshot: the file has completed the journey.
How to run
Save as example1_git_three_states.sh and run bash example1_git_three_states.sh. Read the status codes as they scroll by — that's the entire vocabulary.

Example 2 — diff: what changed, where

The same file edited twice, staged once. Watch the three diff flavors answer three different questions about the same moment.

#!/usr/bin/env bash
set -euo pipefail
demo=$(mktemp -d)/diff-demo && mkdir -p "$demo" && cd "$demo"
git init -q
git config user.email "you@example.com"
git config user.name  "You"
echo "line one"  > file.txt
echo "line two" >> file.txt
git add file.txt
git commit -qm "baseline"

echo "== edit 1, unstaged =="
echo "line three" >> file.txt
echo "--- git diff (working tree vs staging) ---"
git diff

echo "== stage edit 1, then make edit 2 =="
git add file.txt
echo "line four" >> file.txt
echo "--- git diff --cached (what WILL be committed) ---"
git diff --cached
echo "--- git diff (only the new unstaged edit) ---"
git diff
echo "--- git diff HEAD (everything vs the last commit) ---"
git diff HEAD

git commit -qam "edits one and two"
git log --oneline
Explanation of Example 2:
  • After the first edit, bare git diff shows line three — the gap between your file and the staging area.
  • After staging, the same command is silent and git diff --cached takes over: it shows the staged edit (line three) as "what will be committed" — review this before commit.
  • The second edit makes both diffs useful again: --cached shows the old staged half, bare diff the new unstaged half, and diff HEAD stitches them together — your whole distance from the last commit.
  • commit -a at the end sweeps in the unstaged edit and saves everything in one snapshot; log closes the loop.
How to run
Save as example2_git_diff_states.sh and run bash example2_git_diff_states.sh. The four diff outputs in sequence are the lesson — same moment, three questions.

5Advantages

  • Six commands cover 95% of a Git day — the model is small enough to actually hold in your head.
  • Nothing is a mystery: status shows all three areas at once; diff answers any "what's different?" before you commit.
  • The staging area is a review step — you decide what a commit contains, and you can stage half a file (add -p), so commits stay focused and history stays readable.
  • Commit boundaries are honest: a commit is exactly the index — no more, no less — which is what makes "commit half the work" safe.
  • History is addressable: every log entry is a hash you can restore, inspect, compare or branch from.
  • The model transfers everywhere: the same three areas and six verbs power GitHub's UI, IDE integrations and every GUI tool — learn the model once.

6Conclusion

Git's entire core workflow is one diagram: the working directory is where you work, the staging area is where you decide what the next snapshot will contain, and the repository is the snapshot you decided on. init opens the door, status tells you where you are, add and commit move files forward, and log/diff let you read and compare any two points on the way. 

git init           start tracking
git status         where am I?
git diff           what changed (not yet staged)?
git add            stage it
git diff --cached  what will be committed?
git commit -m      save the snapshot
git log            the history
# if you forget everything: status, add, commit, diff

Learn the three areas and the six verbs are just directions on a map you already understand.
