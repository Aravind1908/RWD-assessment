1Introduction

GitHub Flavored Markdown (GFM) is the dialect GitHub renders on every repo, issue, pull request and Discussion page. It's plain core Markdown (headings, emphasis, lists, code, links, images) plus a small set of extensions — and it's the de-facto standard you'll actually meet in the wild.

2Syntax and its Explanation

Task lists

A list item that starts with [ ] (open) or [x] (done) becomes a checkbox. In issues and PRs the boxes are clickable — turning an issue body into a checklist that anyone on the team can tick off.

- [x] Parse the config file
- [x] Add JSON storage
- [ ] Windows path support
- [ ] Write the docs
  • Parse the config file
  • Add JSON storage
  • Windows path support
  • Write the docs

Collapsible sections

GFM accepts raw HTML, and GitHub's signature use of it is the <details>/<summary> pair: content that's hidden until clicked. Full Markdown works inside. Perfect for "Advanced configuration" in a README — visible to those who need it, invisible to everyone else.

<details>
<summary>Advanced configuration (click to expand)</summary>

tasklight reads `~/.config/tasklight/config.json`:

```json
{ "theme": "dark", "sort": "created" }
```

The anatomy of a professional README.md

Every well-regarded open-source README is the same nine parts, in the same order — a landing page for the code:

  1. Title + one-line pitch — what it is, in a sentence
  2. Badges — CI status, version, license (small trust signals, generated by shields.io)
  3. Screenshot / demo — a picture or GIF beats a paragraph
  4. Features — three to five bullets, the reasons to care
  5. Installation — one fenced code block, copy-paste runnable
  6. Quick start / usage — the minimal commands to get value
  7. Advanced — details go in a collapsible section
  8. Contributing — how to help, plus a task list of good first issues
  9. License — the legal line

3Features & Uses

Badges — the trust signals

![Build](https://img.shields.io/github/actions/workflow/status/OWNER/REPO/ci.yml)
![Version](https://img.shields.io/github/v/tag/OWNER/REPO)
![License](https://img.shields.io/github/license/OWNER/REPO)

A badge is just a Markdown image whose URL is generated by shields.io — it queries your repo (CI runs, latest tag, license file) and returns a live status pill. Three badges max; they answer "is this maintained? which version? can I use it?" before anyone reads a word.

Write the README for the stranger who lands at 1 a.m. If they can install and run the tool in under five minutes from the README alone — and if the first screen answers "what is this, does it work, is it safe?" — the file has done its job.

5Advantages

  • One file does the landing page's job — no website build step: the README is the project's front page, rendered for free on GitHub.
  • Interactive, yet plain text — task lists tick themselves off in issues, <details> hides depth on demand, and the source still diffs cleanly in Git.
  • Badges make trust automatic — CI status and version update themselves; a passing green badge is worth a paragraph of "it's maintained!"
  • A standard structure builds credibility — when every section is where readers expect it, the project reads as professional before a line of code is examined.

6Conclusion

GFM is core Markdown plus the extensions GitHub actually uses: task lists (- [ ]) that turn issues into checklists, collapsible sections (<details>/<summary>) that keep depth optional, and the everyday extras — tables, strikethrough, autolinks, emoji, issue references.

A professional README.md is the same nine parts every time: title → badges → screenshot → features → install → quick start → advanced (collapsed) → contributing (with a task list) → license. Nailed in that order, it converts a stranger into a user in five minutes.
