Fork vs Clone — and the Pull Request Workflow

Clone copies a repo you already have access to; a fork is your own copy of someone else's repo on GitHub. The full contribute-to-any-project workflow — fork → clone → branch → commit → pull request — plus a note on GitHub Pages.

Version Control · Git · GitHub Workflow

1Introduction

On a team repo, you clone it and push branches directly — everyone shares one repository. In open source (or any repo you don't own), you don't have write access, so GitHub gives you a fork: a personal copy of the project under your account. You clone your fork, work on it, and propose your changes back to the original with a pull request.

# the shape of a contribution
team/project ──Fork (GitHub button)──▶ you/project ──clone──▶ your laptop
   ▲                                                        │
   └────────────── Pull Request (branch + review + merge) ◀─┘

Once you have the two repos connected, your laptop knows both: origin = your fork, upstream = the original. Everything else is ordinary Git.

2The Complete Workflow, as Commands

# 1. Fork: click the "Fork" button on team/project (GitHub does the copying)

# 2. Clone YOUR fork to your laptop
git clone https://github.com/you/project.git
cd project

# 3. Connect the original, so you can keep up with it
git remote -v                  # origin → your fork
git remote add upstream https://github.com/team/project.git

# 4. Branch and work (never commit to main of the project)
git switch -c feature/add-install
#    …edit files…
git add .
git commit -m "docs: add install section"
git push -u origin feature/add-install   # push to YOUR fork

# 5. Pull Request: on GitHub, "Compare & pull request"
#    team/project ← you/project:feature/add-install
#    → CI runs, maintainers review, you fix feedback (more commits on the

#      same branch), and a maintainer clicks Merge.

# 6. Keep your fork healthy (repeat while the project is alive)
git fetch upstream
git switch main
git merge upstream/main        # bring the project's progress into your fork
git push

What a pull request actually is: a proposal — "here are N commits on a branch of your fork; please merge them into your repo" — plus the review conversation, CI results, and the merge button around it. It is the gate that keeps the original clean: nothing enters the project without review.

Hosting a website with GitHub Pages: GitHub serves any repo as a static website — the same static-hosting model as the hosting guide. Put your site files (an index.html + assets) in your repo, then Settings → Pages → Deploy from a branch (choose /main, or a docs/ folder). Minutes later the site is live at https://you.github.io/repo-name. No server, no billing, no config — it's the classic home for portfolios, project docs, and this series of guides.

3Features & Uses

Fork or clone — which one?

SituationPath
Your team's repo (you have write access)clone it, push feature branches directly, open PRs between branches of the same repo
Open-source project you want to contribute tofork → clone your fork → branch → PR to the original
Just reading/studying someone's codeclone it — no fork needed
Building your own project as a fork of a templatefork the template, then delete the upstream connection if you want a clean history
The two-remote habit: in a fork, push goes to origin (your fork — always safe), and progress from the project is fetched from upstream. Mixing those up is the single most common fork-workflow mistake — pushing to upstream is impossible anyway (you have no write access), which is the built-in safety.

4Example Program

One script simulates the entire workflow on a single machine: two bare repositories play "team/project" (upstream) and "you/project" (the fork), a third clone is your laptop. Built in a temp folder, cleans up after itself.

#!/usr/bin/env bash
set -euo pipefail
root=$(mktemp -d) && cd "$root"

# team/project — the original ("upstream")
git init -q --bare --initial-branch=main team.git
git clone -q team.git seed && cd seed
git config user.email "[email protected]"
git config user.name  "Team"
echo "# project" > README.md
git add README.md
git commit -qm "v1"
git push -q origin main
cd "$root"

# you click "Fork": a copy of the repo appears under your account
git clone -q --bare team.git you.git

# you clone YOUR fork to your laptop
git clone -q you.git laptop && cd laptop
git config user.email "[email protected]"
git config user.name  "You"
git remote add upstream ../team.git   # connect the original

# branch, work, commit, push to your fork
git switch -c feature/add-install
printf "\n## Install\nnpm install\n" >> README.md
git add README.md
git commit -qm "docs: add install section"
git push -u origin feature/add-install

# the pull request = your branch vs the project's main
git fetch upstream
git log --oneline upstream/main..feature/add-install   # what the PR proposes

# a maintainer merges the PR (their clone takes your branch)
cd "$root"
git clone -q team.git maintainer && cd maintainer
git config user.email "[email protected]"
git config user.name  "Team"
git remote add you ../you.git
git fetch you
git merge --no-ff you/feature/add-install -m "Merge PR: add install section"
git push -q origin main
git log --oneline --graph          # the contribution, inside the project now
Explanation:
  • git clone --bare team.git you.git stands in for clicking Fork: a complete copy of the project, owned by "you". The laptop clone then has origin = the fork and upstream = the original.
  • Your commit goes only to origin (the fork) — the original is untouched, exactly like GitHub's permission model.
  • git log upstream/main..feature/add-install is the PR's content: the commits that are proposed for the project.
  • The final merge is what the maintainer's Merge button does: the project's main now carries your branch, and the --graph shows the fork's line joining the project's.
How to run
Save as example1_fork_clone_pr.sh and run bash example1_fork_clone_pr.sh. Only Git is needed; everything happens in a temp folder.

5Advantages

  • Contribute to anything: the fork model lets strangers improve any public project without the owners giving out write access.
  • Safe by permission: you literally cannot break the original repo — your pushes go to your fork, and entry is only via reviewed PRs.
  • Review + CI as a gate: every change gets tested and discussed before it lands; the project's main stays trustworthy.
  • Your fork is a sandbox: experiments, half-finished ideas and learning branches live in your own space, with the project's progress one git fetch upstream away.

6Conclusion

Clone is a copy on your machine; fork is your own copy of someone else's repo on GitHub. The workflow: Fork → clone your fork → add upstream → branch → commit → push to your fork → open a Pull Request → maintainers review and merge. Your laptop's two remotes keep it honest: push to origin, update from upstream.

And the same platform hosts the result: put an index.html in a repo, enable Settings → Pages, and your static website is live at you.github.io/repo — no server required. Fork to copy, PR to propose, Pages to publish.
