Git Branches

Branches are pointers, not copies — which is why they're nearly free. Creating and switching between them, merging in its two forms, and the feature-branch workflow. One simple demo.

Version Control · Git · Branching & Merging

1Introduction

A branch is a movable pointer to a commit — a tiny file containing one hash. Creating a branch writes that file; switching branches re-points your working directory at the branch's commit. Nothing is copied, so branching is nearly free — which is why the healthy habit is a branch per task, each with its own timeline. 

# what a branch actually is
.git/refs/heads/main     →  a1b2c3d
.git/refs/heads/feature  →  a1b2c3d   ← two pointers, same commit: free

Three verbs cover almost everything: create (git switch -c), move between (git switch), and combine (git merge).

2Syntax and its Explanation

Creating and switching

git switch -c feature/login   # create the branch AND switch to it
git switch main               # back to main
git switch -                  # jump to the previous branch
git branch                    # list branches (* = current)
git branch -d feature/login   # delete a fully-merged branch

The old checkout still does all of this (git checkout -b = git switch -c). Modern Git just split the jobs: switch moves branches, git restore file discards file edits.

Merging — two forms

# 1) FAST-FORWARD — your branch didn't move; the pointer slides ahead
main ─A─B
      └─C─D    (feature; main sat still)
git merge feature  →  main ─A─B─C─D        # no new commit, linear

# 2) THREE-WAY — both sides moved, so Git joins the timelines
          B
         / \
    M───/   \──C        (M on main, C on feature)
    A
git merge feature  →  M──X     # X = merge commit with TWO parents

In a three-way merge Git finds the common ancestor, compares each side's changes, and combines them. Different parts of the file → combined automatically. The same lines → Git can't choose for you: that's a merge conflict (next guide).

The feature-branch workflow

git switch main && git pull           # 1. start from fresh main
git switch -c feature/login-fix       # 2. branch
# 3. edit, commit in small steps
git fetch && git merge origin/main    # 4. sync with main while working (repeat!)
git push -u origin feature/login-fix  # 5. share it → open a PR
# 6. review → merge into main
git switch main && git pull
git branch -d feature/login-fix       # 7. done — delete the branch

The discipline in one line: main is always shippable; every branch is a draft. Step 4 — syncing with main while the feature is alive — is what keeps the final merge small.

4Example Program

One script: branch off, work on both sides, merge, and watch the history. Built in a temp folder, cleans up after itself.

#!/usr/bin/env bash
set -euo pipefail
demo=$(mktemp -d)/branches && mkdir -p "$demo" && cd "$demo"
git init -q --initial-branch=main
git config user.email "[email protected]"
git config user.name  "You"
printf "line one\nline two\nline three\nline four\nline five\nline six\nline seven\nline eight\n" > notes.txt
git add notes.txt
git commit -qm "base"

# 1) branch off and work on it
git switch -c feature
sed -i 's/line seven/FEATURE: line seven/' notes.txt
git commit -qam "feature: edit line seven"

# 2) meanwhile, main moves too
git switch main
sed -i 's/line two/LINE TWO (main)/' notes.txt
git commit -qam "main: edit line two"

# 3) merge — both sides moved, so a merge commit joins them
git merge feature
git log --oneline --graph --all
cat notes.txt                        # both edits, present together
Explanation:
  • git switch -c feature created the pointer and moved the working tree — from then on, commits land on feature, not main.
  • Switching back to main makes the feature's edit vanish from disk — it's safe on the branch; the working tree is always "whatever the current branch points at".
  • Both sides now have commits, so the merge is three-way: the --graph log shows the fork and the X-shaped join (a merge commit with two parents).
  • If main had sat still, the same merge would have been a fast-forward — the pointer slides, no new commit, one straight line.
How to run
Save as example1_git_branches.sh and run bash example1_git_branches.sh. The --graph output at the end is the whole story: fork, join, both changes in.

5Advantages

  • Nearly free — a pointer plus new commits. That cost profile is why you branch per task instead of fearing the shared branch.
  • Switch is a time machine — files belonging to other branches reappear when you switch back; nothing is lost by moving.
  • Honest history — fast-forward stays linear when it can; the merge commit records where work happened when it can't. git log --graph always tells the true story.
  • Local and parallel — branch, switch, merge need no network; several people (or one person, two tasks) move at full speed while main only receives finished work.

6Conclusion

A branch is a movable pointer to a commit. git switch -c makes one and moves you to it; git merge combines two histories — a fast-forward (pointer slides, no new commit) when your branch sat still, or a three-way merge (a merge commit joins the two tips) when both moved.

The daily rhythm: fresh main → branch → small commits → sync often → push and review → merge → delete the branch. Main is the promise that the project always works; every branch is a draft on its way there.
