Git Merge Conflicts

Two people changed the same lines in different ways, and Git stopped to ask which version wins. What the markers mean, the steps to resolve it, and one simple demo.

Version Control · Git · Conflicts

1Introduction

A merge conflict happens when both sides of a merge changed the same part of a file in different ways. Git can combine non-overlapping changes automatically — but where changes overlap it cannot guess which intent wins, so it marks the disputed region in the file, pauses the merge, and leaves the decision to you.

It is not an error state: no data is lost, both versions remain in history, and the merge can always be undone with git merge --abort. A conflict is Git asking for a decision only a human can make. 

# what Git writes into a conflicted file:
line one
<<<<<<< HEAD
MAIN: my copy of line two
=======
FEATURE: their copy of line two
>>>>>>> feature
line three

2The Markers and the Resolution Steps

The three parts of a conflict

MarkerMeans
<<<<<<< HEADtop of the dispute — the branch you're on
=======the divider
>>>>>>> featurebottom — the branch being merged in

Between the first and last marker: two versions of the same region. Lines outside the markers merged cleanly — leave them alone. A file can have several such hunks.

The resolution steps

# 1. the merge stops
git merge feature
#    CONFLICT (content): Merge conflict in notes.txt

# 2. see what's conflicted
git status                    # "both modified: notes.txt" — your work queue

# 3. open the file, read the markers, decide line by line
#    (keep mine / keep theirs / write the correct third version)

# 4. save the file with the markers REMOVED
git add notes.txt             # 5. staging the clean file = "resolved"
git commit                    # 6. complete the merge (message pre-filled)
# 7. run the tests, then push

Shortcuts and the panic button

CommandWhat it does
git checkout --ours notes.txttake your whole version of the file
git checkout --theirs notes.txttake the incoming branch's whole version
git mergetoolopen a visual diff tool with accept buttons
git merge --abortundo the whole merge — back to the pre-merge state, any time during one
During a rebase the words ours/theirs swap. When in doubt, read the markers — they never lie.

3Features & Uses

Where conflicts come from

SituationHow often
Both sides edit the same linesthe classic ~80%
Both sides add a file with the same name, different contentcommon for new helpers/tests
One side edits a file, the other deletes itdecide consciously: keep or drop
Resolve on the feature branch, never on main — if a PR shows conflicts, merge main into your branch, resolve, push. And keep conflicts small by habit: short features, and sync with main daily (git fetch && git merge origin/main).

4Example Program

One script: create a real conflict, read the markers, resolve it, finish the merge. Built in a temp folder, cleans up after itself.

#!/usr/bin/env bash
set -euo pipefail
demo=$(mktemp -d)/conflict && mkdir -p "$demo" && cd "$demo"
git init -q --initial-branch=main
git config user.email "you@example.com"
git config user.name  "You"
printf "line one\nline two\nline three\n" > notes.txt
git add notes.txt
git commit -qm "base"

# two sides rewrite the SAME line, differently
git switch -c feature
sed -i 's/line two/FEATURE copy/' notes.txt
git commit -qam "feature: rewrite line two"
git switch main
sed -i 's/line two/MAIN copy/' notes.txt
git commit -qam "main: rewrite line two"

echo "== the merge stops: conflict =="
git merge feature || true       # expected: the merge "fails"
git status --short              # UU notes.txt — both modified, unmerged
cat notes.txt                   # the markers appear here

echo "== resolve: keep both, drop the markers =="
printf "line one\nMAIN copy\nFEATURE copy\nline three\n" > notes.txt
git add notes.txt               # staging the clean file = "resolved"
git commit -qm "Merge branch 'feature'"
git log --oneline --graph       # the merge commit, with the decision inside
Explanation:
  • The || true lets the script continue after the merge "fails" — a conflict is the expected outcome, not a crash.
  • UU notes.txt in status means unmerged on both sides — every UU file in the list is one decision to make.
  • Reading the markers: HEAD is main's rewrite (the branch we're on), the bottom is feature's. The resolution — "keep both as two lines" here, but equally valid: one side, or a new third version — is whatever you save.
  • git add + git commit finish the merge: the final --graph shows the merge commit carrying the decision into history.
How to run
Save as example1_git_merge_conflict.sh and run bash example1_git_merge_conflict.sh. The middle of the output — the file with markers — is the whole lesson. (If you ever want out mid-merge: git merge --abort.)

5Advantages

  • Safe by design — Git fails loudly and reversibly: both versions stay in history, and --abort is always available. "Let me just try the merge" is a zero-risk experiment.
  • The decision is visible — the markers show both options in the file itself, and the merge commit records what was chosen.
  • Graded tooling — line-by-line edits for real decisions, --ours/--theirs for whole files, mergetool and editor support (VS Code's inline buttons) for visual comfort.
  • Preventable by schedule — short features plus daily syncs shrink each merge; the 400-line conflict is almost always a branch that ignored main for weeks.

6Conclusion

A merge conflict is Git saying: you both changed the same lines — decide. The steps: merge → status → read the markers → save the file without markers → add → commit, with --ours/--theirs for whole-file calls and git merge --abort as the guaranteed exit.

The real skill is the discipline around it: short features, sync with main often, resolve on the feature branch, and treat every conflict as a small product decision worth making deliberately.
