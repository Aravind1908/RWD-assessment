Tailwind CSS: The Three Setup Methods

Play CDN, CLI, and PostCSS — how each one works, step by step, side by side, and exactly when each method is the appropriate choice.

CSS Framework · Tailwind · Setup Methods

1Introduction

Tailwind doesn't work like a normal stylesheet you copy from a website — the CSS is generated for your project, keeping only the utility classes you actually use. That "generation" needs a mechanism, and Tailwind offers three standard setup methods, each aimed at a different situation:

  • Play CDN — one <script> tag; Tailwind compiles in the browser at runtime. No build, no install.
  • CLI — one watched command that compiles a small input file into a purged output.css. Light build, no bundler.
  • PostCSS — Tailwind plugs into your existing build tool (Vite, webpack) as a PostCSS plugin. The full production pipeline.

All three let you write the same utility-class HTML. The difference is where and when the CSS is compiled — and therefore which one is appropriate for your project. (The philosophy behind those utility classes is covered in the companion document, css_tailwind_utility_first.html.)

2Syntax and its Explanation

The pipeline all three methods share

your HTML/templates  ──
                       ├──▶  Tailwind scanner  ──▶  CSS containing
your input.css  ───────┘        (purging)            ONLY the utilities
                                                        you actually use

Two inputs matter everywhere: your HTML (so the scanner knows which utility classes appear) and a tiny CSS entry file. Methods differ only in who runs the scanner and when:

Play CDNCLIPostCSS
Who runs the scannera script in the user's browsera command on your machineyour build tool (Vite/webpack)
When it runsruntime, on every page loadon save, while you workon save (dev) + at build time
What ships to usersHTML + the CDN script (full CSS, compiled in-browser)HTML + a static output.cssHTML + built, purged CSS

The one CSS entry file (Tailwind v4)

/* input.css — used by BOTH the CLI and PostCSS methods */
@import "tailwindcss";

In v4 this single line is the entire "config" — design tokens and customization live in CSS via @theme instead of a JavaScript file. (If you're using Tailwind v3, the entry file uses three directives — @tailwind base; @tailwind components; @tailwind utilities; — and a tailwind.config.js with a content glob tells the scanner where your templates live.)

Quick syntax reference for each method

<!-- Play CDN: the entire setup -->
<script src="https://cdn.tailwindcss.com"></script>

# CLI (v4): compile + watch
npx @tailwindcss/cli -i ./input.css -o ./dist/output.css --watch

# PostCSS (v4): plugin config, then your build tool does the rest
// postcss.config.js
export default { plugins: { '@tailwindcss/postcss': {}, 'autoprefixer': {} } }
Key rule: the CDN gives you the fastest start but ships the most CSS (nothing is purged, compilation happens in the visitor's browser). The CLI and PostCSS both give you the same purged production CSS — pick between them by whether your project already has a build tool.

3Features & Uses

Method 1 — Play CDN (no build at all)

One script tag, added to <head>. The script watches the DOM and compiles utility CSS in the browser as you edit. You can even configure it inline:

<script src="https://cdn.tailwindcss.com"></script>
<script>
  // optional: extend the theme without any build
  tailwind.config = {
    theme: { extend: { colors: { brand: "#2563eb" } } }
  }
</script>
  • Appropriate when: learning Tailwind, quick prototypes, demos/talks, CodePen/JSFiddle experiments, emails, throwaway pages.
  • Not appropriate when: any production site — it ships the entire utility CSS (no purging), compiles at runtime in each visitor's browser, and prints a console warning that says exactly this.

Method 2 — CLI (one command, no bundler)

The Tailwind CLI compiles your input CSS into a purged, production-ready stylesheet and can watch for changes. No PostCSS, no webpack — ideal for static sites and simple multi-page sites.

# 1. write input.css →  @import "tailwindcss";

# 2. install the CLI
npm install -D tailwindcss @tailwindcss/cli

# 3. compile + watch (v4)  — v3 used: npx tailwindcss
npx @tailwindcss/cli -i ./input.css -o ./dist/output.css --watch
<link rel="stylesheet" href="dist/output.css">
  • Appropriate when: static sites, personal pages, small marketing sites, or whenever you want real purged CSS with the least possible machinery.
  • Not appropriate when: you're already inside a Vite/webpack project — don't run a second build alongside it; let the existing pipeline handle Tailwind via the PostCSS route.

Method 3 — PostCSS (the full production pipeline)

Tailwind plugs into your existing build as a PostCSS plugin. Your CSS entry is a normal source file processed at build time — the standard route for real applications.

# install the plugin (v4)
npm install -D tailwindcss @tailwindcss/postcss autoprefixer

# postcss.config.js
export default {
  plugins: { '@tailwindcss/postcss': {}, 'autoprefixer': {} }
}

# src/input.css
@import "tailwindcss";
  • Appropriate when: production apps, SPAs, React/Vue/Svelte projects, anything already built with Vite, webpack, or esbuild. (In Vite you'll usually add the @tailwindcss/vite plugin instead — same idea, tighter integration, still "the PostCSS-family route".)
  • Not appropriate when: a single throwaway HTML page — that's overkill; the Play CDN is the right tool there.

The three methods form a natural upward path: learn and prototype on the CDN → move a real static site to the CLI → move a growing app to PostCSS. The HTML you write never changes along the way — only the build gets more serious.

Did you know? The Play CDN's console warning is honest about its limits: it's a JIT compiler running in the visitor's browser, so first paint includes a compile step and the shipped CSS isn't purged. For learning that's a feature (you see everything instantly); for production it's the reason the CLI and PostCSS methods exist.

4Example Programs with Explanation

Example 1 — Starter page with the Play CDN (Method 1)

The fastest possible start: a single HTML file with the CDN script, an inline theme extension, and a small page built purely from utilities. Save as index.html and open in a browser with internet access.

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Tailwind Starter — Play CDN</title>
  <!-- Method 1: the entire setup is this one tag -->
  <script src="https://cdn.tailwindcss.com"></script>
  <!-- optional inline config: add a "brand" color -->
  <script>
    tailwind.config = {
      theme: { extend: { colors: { brand: "#2563eb" } } }
    }
  </script>
</head>
<body class="bg-gray-50 min-h-screen flex flex-col">

  <nav class="max-w-4xl w-full mx-auto flex items-center
            justify-between px-6 py-4">
    <span class="font-bold text-brand">acme.</span>
    <a href="#" class="bg-brand hover:bg-blue-700 text-white text-sm
        font-semibold px-4 py-2 rounded-lg transition">Sign up</a>
  </nav>

  <main class="flex-1 flex items-center justify-center px-6 pb-16">
    <div class="bg-white rounded-2xl shadow p-10 max-w-md w-full text-center">
      <h1 class="text-3xl font-bold">Hello from Tailwind</h1>
      <p class="mt-3 text-gray-600">
        This page uses zero hand-written CSS — every style is a
        utility class. text-brand is a custom color from the
        inline config above.
      </p>
      <div class="mt-8 flex flex-col sm:flex-row justify-center gap-3">
        <button class="bg-brand hover:bg-blue-700 text-white font-semibold
                    py-3 px-6 rounded-xl transition">Primary</button>
        <button class="border border-gray-300 hover:border-blue-600
                    hover:text-blue-600 font-semibold py-3 px-6
                    rounded-xl transition">Secondary</button>
      </div>
    </div>
  </main>
</body>
</html>
Explanation of Example 1:
  • The CDN script is the only setup — no npm, no CSS file, no config file.
  • The inline tailwind.config adds a brand color, showing that even the CDN route is customizable: text-brand, bg-brand, and hover:bg-blue-700 all work immediately.
  • sm:flex-row on the button row demonstrates responsive modifiers with no media queries written.
  • Because compilation happens in the browser, you can open this in CodePen and watch styles update as you type — the ideal learning loop.
How to run
Save as index.html and open in a browser with internet (the CDN downloads Tailwind). Resize below 640px to see the buttons stack. Note the console warning from the CDN script — it's the framework telling you "great for prototyping, use a real build for production", which is exactly when you'd move to Method 2 or 3.

Example 2 — Production setup with PostCSS + Vite (Method 3)

A real, minimal project — four files. Vite runs PostCSS → @tailwindcss/postcss → Tailwind: hot reload while developing, and a purged, minified stylesheet at build time. (Method 2, the CLI, would replace Vite with the single npx @tailwindcss/cli command and the same input.css.)

# ── project structure ─────────────────────────────
my-app/
├── package.json
├── postcss.config.js
└── src/
    ├── input.css
    └── index.html

# ── 1. package.json ───────────────────────────────
{
  "name": "my-tailwind-app",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build"
  },
  "devDependencies": {
    "tailwindcss": "^4.0.0",
    "@tailwindcss/postcss": "^4.0.0",
    "autoprefixer": "^10.4.20",
    "postcss": "^8.4.49",
    "vite": "^6.0.0"
  }
}

# ── 2. postcss.config.js ──────────────────────────
export default {
  plugins: {
    '@tailwindcss/postcss': {},
    'autoprefixer': {}
  }
}

# ── 3. src/input.css (the whole "config") ─────────
@import "tailwindcss";
<!-- ── 4. src/index.html ────────────────────────── -->
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Tailwind via PostCSS</title>
  <link rel="stylesheet" href="/src/input.css">
</head>
<body class="bg-gray-100 p-8">
  <h1 class="text-3xl font-bold text-blue-700">Tailwind via PostCSS</h1>
  <p class="mt-2 text-gray-600">
    Built by a real PostCSS pipeline — purged, small CSS for production.
  </p>

  <!-- two pricing cards: stacked on mobile, side-by-side from md -->
  <div class="mt-6 flex flex-col md:flex-row gap-4">
    <div class="bg-white p-6 rounded-xl shadow w-full md:w-56">
      <h2 class="font-semibold text-lg">Plan A</h2>
      <p class="text-sm text-gray-500 mt-1">Starter utilities</p>
      <button class="mt-4 bg-blue-600 hover:bg-blue-700 text-white text-sm
                  font-medium py-2 px-4 rounded-lg">Choose</button>
    </div>
    <div class="bg-white p-6 rounded-xl shadow w-full md:w-56">
      <h2 class="font-semibold text-lg">Plan B</h2>
      <p class="text-sm text-gray-500 mt-1">More utilities</p>
      <button class="mt-4 bg-gray-800 hover:bg-gray-900 text-white text-sm
                  font-medium py-2 px-4 rounded-lg">Choose</button>
    </div>
  </div>
</body>
</html>
Explanation of Example 2:
  • @import "tailwindcss"; in src/input.css is all the CSS source you need — v4 keeps its configuration in CSS (@theme), so there's no tailwind.config.js to maintain.
  • Vite processes input.css through PostCSS → @tailwindcss/postcss → Tailwind, which scans index.html and keeps only the utilities that appear.
  • flex-col md:flex-row stacks the cards on phones and lays them out side by side from md — the same responsive pattern as Example 1, now compiled at build time.
  • npm run build outputs dist/ with a purged, minified stylesheet — often only a few KB for a whole page. That's the production advantage the CDN can't offer.
  • Tailwind v3 note: same project shape, but input.css uses the three directives @tailwind base; @tailwind components; @tailwind utilities; and a tailwind.config.js holds the content glob.
How to run
Create the four files exactly as shown, then run: npm install → npm run dev (hot-reload dev server) → npm run build (production build into dist/). No CDN and no internet needed after the initial npm install. A ready-made version of this project is in the workspace folder tailwind_postcss_starter/.

5Advantages

  • The right tool for every stage: the three methods match the lifecycle of a project — zero-setup learning (CDN) → real static sites (CLI) → full applications (PostCSS) — without ever changing the HTML you write.
  • Fastest possible feedback loop: the Play CDN compiles in the browser, so learning and prototyping have no setup friction at all — open a file, type a class, see it.
  • Production CSS without a bundler: the CLI gives you the same purged output as a full build pipeline for sites that don't need one — less tooling to learn and maintain.
  • Native framework integration: via PostCSS (or the @tailwindcss/vite plugin), Tailwind becomes just another part of the build you already have — hot reload, tree-shaken output, cache-busting, all for free.
  • Small, lean output everywhere it matters: both real-build methods output only used utilities, keeping production CSS tiny (often 5–15 KB) and page loads fast.
  • No dead end: migrating "up" (CDN → CLI → PostCSS) is a build-config change, not a rewrite — your utility-class markup carries over untouched.

6Conclusion

All three setup methods compile the same utility-class HTML — they differ only in who runs the scanner and when: the Play CDN runs it in the visitor's browser (fastest start, no purging), the CLI runs it on your machine with one watched command (purged CSS, no bundler), and PostCSS runs it inside your existing Vite/webpack build (purged CSS plus full hot reload and framework integration).

In summary: learn and prototype with the Play CDN, ship static sites with the CLI, and ship applications with PostCSS. Prototype with the CDN, ship with a build — and remember your HTML never changes as you move between them.
