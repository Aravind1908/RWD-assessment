Tailwind CSS: tailwind.config.js

The three keys every project actually uses — content (what to scan and purge), theme.extend (custom colors, fonts, spacing) and plugins — shown live in the browser and in a real build.

CSS Framework · Tailwind · Configuration

1Introduction

A Tailwind project is a framework plus a build step. The build reads one file — tailwind.config.js — and everything you tell it there shapes the CSS it generates: which files contain your class names, which design tokens exist, and which extra utilities the framework gains.

Three keys cover most real configs: content, theme.extend and plugins. Everything else you'll ever touch — screens, shadows, radii — is a token under theme. 

/** @type {import('tailwindcss').Config} */
export default {
  content: ['./index.html', './src/**/*.{js,ts,jsx,tsx}'],
  theme: {
    extend: { colors: { brand: '#2563eb' } },
  },
  plugins: [],
}

In v3 this is a JavaScript file at the project root, found automatically. In v4 the same three ideas moved into CSS — content is auto-detected, tokens live in @theme — so the file becomes optional; the note in Section 2 maps each key to its v4 home.

2Syntax and its Explanation

content — what Tailwind scans (why unused styles disappear)

The build scans every file matching the content globs, extracts every string that looks like a utility name, and generates CSS only for the classes it finds. Anything it never sees is never emitted — that's the purge, and it's why a small page ships a few kilobytes of CSS instead of the whole framework.

Note what's not a separate step: dev builds include the full framework (fast iteration), production (minified) builds contain only used classes. "Purging" is simply what production mode means. 

export default {
  content: [
    './index.html',
    './src/**/*.{js,ts,jsx,tsx}',   // every file that can hold class names
  ],
}

The globs decide the universe. Add every place class names can appear — server components, template files, a shared design-system package — and nothing you render gets purged away. In v3.3+ you can also mark paths relative to the config and ignore generated files. 

// class names built at runtime never appear literally → they'd be purged.
// safelist rescues exactly the classes you generate dynamically:
safelist: [
  'bg-green-500',
  { pattern: /^bg-(red|blue|green)-500$/, variant: ['hover'] },
]

The pattern entry matches every string the regex describes — the classic fix for bg-${status}-500, a class name that exists nowhere in any file.

theme.extend — your brand as tokens

theme is the full set of scales the utilities draw from — colors, spacing, screens, fonts, shadows, radii. Assigning a category directly replaces the entire scale; extend merges yours in alongside the defaults. Almost always use extend: you keep every gray and blue while adding your own. 

theme: {
  extend: {
    colors: {
      brand: { 50: '#eff6ff', 500: '#2563eb', 600: '#1d4ed8', 950: '#172554' },
    },
    fontFamily: {
      display: ['"Trebuchet MS"', 'Verdana', 'sans-serif'],
    },
    spacing: {
      gutter: '1.25rem',   // p-gutter, gap-gutter …
      18: '4.5rem',        // numeric keys: × 0.25rem in v3
    },
  },
}
  • colors — a named color becomes a family: bg-brand-500, text-brand-950, and opacity modifiers work on it (bg-brand-500/50).
  • fontFamily — the array is a fallback chain (load the fonts via @font-face or a <link>); the key becomes a utility, font-display.
  • spacing — every key joins the spacing scale, so p-gutter works anywhere p-4 does.

plugins — add utilities, or borrow a community one

A plugin is a function the build runs to register extra utilities, variants or component styles — the same hooks the framework itself uses. The useful ones are npm packages; the simple ones fit in five lines. 

plugins: [
  require('@tailwindcss/forms'),   // normalizes inputs, selects, checkboxes
  function ({ addUtilities }) {
    addUtilities({
      '.text-shadow': { textShadow: '0 2px 4px rgba(0,0,0,0.25)' },
    })
  },
]

@tailwindcss/forms is the canonical "plugin that earns its keep": one require and every input, select and checkbox looks consistent and accessible. The custom plugin shows the shape — receive the API (addUtilities, addVariant, theme) and register what you want.

4Example Programs with Explanation

Example 1 — theme.extend in the browser (Play CDN)

The Play CDN reads a tailwind.config global with the same shape as the file, so custom tokens work in a single HTML file — no build. Save as index.html (needs internet).

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>theme.extend — Play CDN</title>
  <script src="https://cdn.tailwindcss.com"></script>
  <script>
    /* the Play CDN reads the same shape as tailwind.config.js */
    tailwind.config = {
      theme: {
        extend: {
          colors: { brand: { 50:'#eff6ff', 500:'#2563eb', 600:'#1d4ed8', 950:'#172554' } },
          fontFamily: { display: ['"Trebuchet MS"','Verdana','sans-serif'] },
          spacing: { gutter: '1.25rem' },
        }
      }
    }
  </script>
</head>
<body class="bg-gray-50 p-gutter text-gray-900">
  <div class="max-w-md mx-auto mt-10 bg-white border border-gray-200
              rounded-2xl p-6 shadow-sm">
    <h1 class="font-display text-2xl font-bold text-brand-950">Custom tokens</h1>
    <p class="mt-2 text-sm text-gray-600">
      Brand colors, a display font and a gutter spacing key —
      none of these exist in Tailwind's defaults.
    </p>
    <div class="mt-5 flex items-center gap-3">
      <button class="bg-brand-600 hover:bg-brand-500 text-white text-sm
                  font-semibold px-4 py-2 rounded-lg">Brand button</button>
      <span class="bg-brand-500/10 text-brand-600 text-xs font-mono
                  px-2 py-1 rounded">bg-brand-500/10</span>
    </div>
  </div>
</body>
</html>
Explanation of Example 1:
  • The CDN config object is a tailwind.config.js minus the wrapper — prototype the tokens here, then paste the same object into the real file.
  • brand is defined with four shades, so bg-brand-600, text-brand-950 and the opacity modifier bg-brand-500/10 all resolve.
  • fontFamily.display becomes the font-display utility; spacing.gutter becomes p-gutter — named keys join the same scale as p-4.
  • The <body> itself uses p-gutter: the custom token is doing layout work from line one.
How to run
Save as index.html and open in a browser with internet. Add a 700 shade to brand and a second spacing key — the CDN recompiles instantly, which is what makes it good for token prototyping.

Example 2 — A real build: config + PostCSS + page

The production shape: tailwind.config.js declares the content globs, a safelist and the tokens; PostCSS runs the build; the page uses the custom utilities and the forms plugin. In a minified build the CSS contains only the classes this page uses.

// tailwind.config.js
export default {
  content: ['./index.html', './src/**/*.{js,ts,jsx,tsx}'],
  safelist: [{ pattern: /^bg-(red|blue|green)-500$/ }],
  theme: {
    extend: {
      colors: { brand: { 50:'#eff6ff', 500:'#2563eb', 600:'#1d4ed8', 950:'#172554' } },
      fontFamily: { display: ['"Trebuchet MS"','Verdana','sans-serif'] },
      spacing: { gutter: '1.25rem' },
    }
  },
  plugins: [require('@tailwindcss/forms')],
}
// postcss.config.js
module.exports = {
  plugins: { tailwindcss: {}, autoprefixer: {} },
}
// input.css
@tailwind base;
@tailwind components;
@tailwind utilities;
<!-- index.html -->
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <link rel="stylesheet" href="css/tailwind.css">
</head>
<body class="bg-gray-50 p-gutter text-gray-900">
  <main class="max-w-md mx-auto mt-10 bg-white rounded-2xl
               border border-gray-200 p-6 shadow-sm">
    <h1 class="font-display text-2xl font-bold">Production build</h1>
    <p class="mt-2 text-sm text-gray-600">
      The CSS on this page contains only the classes it uses.
    </p>
    <input class="mt-4 w-full rounded-lg border-gray-300 text-sm"
           placeholder="the forms plugin styles me">
    <button class="mt-3 bg-brand-600 hover:bg-brand-500 text-white
                text-sm font-semibold px-4 py-2 rounded-lg">Save</button>
  </main>
</body>
</html>
Explanation of Example 2:
  • content lists every file that can contain class names — the build scans them all and emits CSS for nothing else; a page this small typically lands at 5–15 KB minified.
  • The safelist pattern rescues classes built at runtime (bg-${status}-500) that no scanner would ever find in a file.
  • plugins: [require('@tailwindcss/forms')] is why the <input> looks right with almost no classes — the plugin styles form elements directly.
  • Dev vs production: npx tailwindcss --watch (unminified) is fast and complete; add --minify and you get the shipped, purged CSS.
How to run
This one needs a build: in a folder with a package.json, run npm install -D tailwindcss@3 postcss autoprefixer @tailwindcss/forms, create the four files above, then npx tailwindcss -i input.css -o css/tailwind.css --minify. The tailwind_postcss_starter folder in this workspace already has the pipeline — drop this config in and run npm run dev. Open css/tailwind.css: it contains exactly this page's classes.

5Advantages

  • Purging is the default, not a feature: production CSS contains only classes found in your content files — typically 5–15 KB per page, instead of a full component sheet.
  • Design tokens, centralized: brand colors, fonts and spacing are declared once; extend keeps every default scale intact while you add your own.
  • Safe dynamic classes: safelist patterns rescue bg-${status}-500 without shipping the entire color system.
  • Plugins are shareable capabilities: forms, typography, daisyUI — one require for behavior consistent across the app.
  • One shape, two worlds: the same config object runs on the Play CDN and in the PostCSS build, so prototypes and production never disagree.
  • It's code: versioned, reviewed, diffable — your design system as a file you can change in a pull request.

6Conclusion

tailwind.config.js answers three questions: where are my class names? (content — the scanner's universe, and therefore what gets purged), what tokens do I have? (theme.extend — colors, fonts and spacing merged into the defaults), and what extra capabilities do I need? (plugins — community packages or five-line customs). The skeleton to memorize: 

export default {
  content: ['./index.html', './src/**/*.{js,ts,jsx,tsx}'],
  theme: { extend: { colors: {}, fontFamily: {}, spacing: {} } },
  plugins: [],
}

In v4 the same three answers live in CSS — auto-detected content, @theme tokens, @plugin. The mental model doesn't change: Tailwind generates CSS from what your config says exists and your files actually use.
