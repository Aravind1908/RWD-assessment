Tailwind CSS: State Variants

How hover:, focus:, active:, group-hover: and dark: let one element react to its state — no &:hover selectors, no extra CSS — with examples and a note on the typography plugin and Headless UI.

CSS Framework · Tailwind · Variants & Ecosystem

1Introduction

A static page is one thing; a page that reacts is an interface. Tailwind handles reactivity with state variants: a prefix in front of any utility that says "apply this only while the element is in this state". hover:bg-blue-700 means "use blue-700 as the background only while hovered".

The syntax is always the same shape — state:utility — and states can be stacked, and stacked with responsive prefixes too: md:hover:bg-blue-800 reads as "at md and up, while hovered, use blue-800". That's the entire mental model: variant(s) first, the utility last. 

/* hand-written CSS */
.btn { background: #2563eb; }
.btn:hover  { background: #1d4ed8; }
.btn:focus  { outline: 2px solid #3b82f6; }

<!-- Tailwind: same behavior, one class list -->
<button class="bg-blue-600 hover:bg-blue-700 focus:ring-2
            focus:ring-blue-500">Click</button>

2Syntax and its Explanation

The state variants

VariantActive when…Typical use
hover:the pointer is over the elementbuttons darken, links underline, cards lift
focus:the element has focus (click or Tab)focus rings on buttons, inputs, links
focus-visible:focus from the keyboard (not mouse)show rings only for keyboard users — the accessibility-favorite
active:the element is pressed / touch-down"pressed" feedback: darker color, slight scale-down
disabled:the element is disabledgrayed-out buttons, muted text
group-hover:a parent marked group is hoveredcard hover moves the arrow, reveals an action
peer-checked: (bonus)a previous sibling marked peer is checkedcheckbox toggles a panel's styles
dark:dark mode is activethe whole page's dark theme, per-element

group-hover — the parent-reacts pattern

Two steps: put group on the parent, and any child can use group-hover:*. This is how you style a child from a parent's hover — the Tailwind version of .card:hover .arrow { … }:

<a class="group block p-4 border border-gray-200 rounded-xl
          hover:border-blue-300">
  <!-- child reacts when the PARENT is hovered -->
  <span class="text-gray-900 group-hover:text-blue-600">Read more</span>
  <span class="inline-block transition-transform
              group-hover:translate-x-1">→</span>
</a>

Multiple groups can be named (group/card + group-hover/card:*) when a card is nested inside another hoverable element.

dark: — the dark-theme variant

dark: applies its utility while dark mode is active. In v4 the default is the visitor's OS preference (prefers-color-scheme) — zero setup. For a manual class-based toggle, v4 adds one CSS line and you toggle the dark class on <html> (v3 used darkMode: "class" in the config):

/* v4: opt into class-based dark mode */
@custom-variant dark (&:where(.dark, .dark *));

<body class="bg-white dark:bg-gray-950
            text-gray-900 dark:text-white">

Stacking order

Convention is breakpoint:state:utility — e.g. md:group-hover:bg-blue-100. Multiple states on one element are just multiple classes: hover:bg-blue-700 active:bg-blue-800 focus:ring-2 focus:ring-blue-500. Pair every state change with transition so it animates instead of snapping.

Key rule: hover is for the mouse, focus is for the keyboard — never remove focus styling (focus:outline-none) without replacing it (focus:ring-2). Keyboard users have no hover; the focus ring is their cursor.

Short note — @tailwindcss/typography

Utilities shine on UI, but styling a whole article by hand (every <h2>, <blockquote>, <table>…) is tedious. The typography plugin adds one class, prose, that auto-styles long-form content — headings, paragraphs, lists, links, code, tables — using the same Tailwind scale.

# v4: npm i -D @tailwindcss/typography, then in your CSS:
@plugin "@tailwindcss/typography";
// (v3: require("@tailwindcss/typography") in tailwind.config plugins)

<article class="prose prose-blue max-w-prose
             dark:prose-invert">
  …raw HTML or rendered Markdown…
</article>

Modifiers: prose-sm/prose-lg (density), prose-blue (accent color), prose-invert (dark). It's the standard companion for blogs and docs inside a Tailwind app: utilities for the chrome, prose for the content.

Short note — Headless UI

Headless UI (by the Tailwind team, for React and Vue) provides unstyled components — Dialog/modal, Disclosure, Listbox, Menu, Popover, Switch, Tab — with all the hard parts done: keyboard navigation, focus trapping, Escape handling, ARIA attributes. npm i @headlessui/react, drop in a <Dialog>, and you add the Tailwind classes yourself — which is exactly where this guide's variants get used: group on the panel, focus-within:ring-2 on the trigger, dark: on every surface.

In short: Headless UI owns the behavior, Tailwind owns the look. Together they're the most common way to build accessible, custom-looking interactive components.

Did you know? focus-visible: (the :focus-visible pseudo-class) is why modern sites only show focus rings when you Tab around but not when you click — browsers decide "this user needs it" for you. It's the single highest-value accessibility variant for links and buttons.

4Example Programs with Explanation

Example 1 — Buttons and cards with every state

One page exercising hover:, active:, focus: and group-hover: on a button, a card, and an input. Save as index.html (needs internet for the CDN).

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Tailwind State Variants</title>
  <script src="https://cdn.tailwindcss.com"></script>
</head>
<body class="bg-gray-50 p-8 text-gray-900">
<div class="max-w-md mx-auto space-y-6">

  <!-- hover: + active: + focus: on one button -->
  <div class="bg-white rounded-2xl border border-gray-200 p-6">
    <h2 class="font-semibold">Primary button</h2>
    <p class="text-xs text-gray-400 mt-1">
      hover: darker · active: pressed · focus: ring (Tab to it)
    </p>
    <button class="mt-4 bg-blue-600 hover:bg-blue-700 active:bg-blue-800
                active:scale-95 text-white font-semibold px-6 py-3 rounded-lg
                transition focus:outline-none focus:ring-2
                focus:ring-blue-500 focus:ring-offset-2">
      Press me
    </button>
  </div>

  <!-- group-hover: parent hovered, children react -->
  <div class="group bg-white rounded-2xl border border-gray-200 p-6
              hover:border-blue-300 transition">
    <h2 class="font-semibold">Card with group-hover</h2>
    <p class="text-sm text-gray-500 mt-1">
      Hover the whole card — the title turns blue and the arrow moves.
    </p>
    <p class="mt-4 inline-flex items-center gap-2 font-medium
                text-gray-900 group-hover:text-blue-600 transition">
      Read more
      <span class="transition-transform group-hover:translate-x-1">→</span>
    </p>
  </div>

  <!-- focus: on a form field -->
  <div class="bg-white rounded-2xl border border-gray-200 p-6">
    <h2 class="font-semibold">Focus ring on input</h2>
    <input type="text" placeholder="Click or Tab into me"
      class="mt-4 w-full border border-gray-300 rounded-lg px-4 py-2
             text-sm focus:outline-none focus:ring-2 focus:ring-blue-500
             focus:border-blue-500">
  </div>
</div>
</body>
</html>
Explanation of Example 1:
  • The button stacks three states: hover: darkens, active: darkens more and scale-95 gives a "pressed" squash, and focus: draws an offset ring when you Tab to it. One transition class animates all of it.
  • The card is the group pattern: the parent has group + its own hover: border; two children react via group-hover:text-blue-600 and group-hover:translate-x-1 — no CSS selectors, no &:hover .child.
  • The input shows the form-field recipe: neutral border at rest, blue border + ring on focus: — the standard accessible input treatment.
How to run
Save as index.html and open in a browser with internet. Hover the card, press-and-hold the button, and press Tab three times to see the focus rings. Try swapping the button's focus:ring-2 for focus-visible:ring-2 and compare click-focus vs keyboard-focus.

Example 2 — A page that follows dark mode

Every surface carries a dark: twin. With v4's default strategy, the page simply follows your OS appearance — toggle your system's dark mode and watch it repaint.

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Dark Mode with Tailwind</title>
  <script src="https://cdn.tailwindcss.com"></script>
</head>
<body class="bg-gray-50 dark:bg-gray-950 p-8 transition-colors">
<div class="max-w-md mx-auto">
  <p class="text-xs font-semibold tracking-widest uppercase
              text-blue-600 dark:text-blue-400">dark: variant</p>
  <h1 class="mt-3 text-3xl font-bold text-gray-900
              dark:text-white">
    Toggle your OS dark mode — this page follows.
  </h1>

  <!-- every element carries a dark: twin -->
  <div class="mt-6 bg-white dark:bg-gray-900 border border-gray-200
              dark:border-gray-800 rounded-2xl p-6">
    <h2 class="text-lg font-semibold text-gray-900 dark:text-white">
      One element, two themes
    </h2>
    <p class="mt-2 text-sm text-gray-600 dark:text-gray-400">
      bg-white → dark:bg-gray-900 · text-gray-900 → dark:text-white ·
      border-gray-200 → dark:border-gray-800
    </p>
    <button class="mt-4 bg-blue-600 hover:bg-blue-700 dark:bg-blue-500
                dark:hover:bg-blue-400 text-white text-sm font-semibold
                px-5 py-2 rounded-lg transition">
      Light and dark buttons
    </button>
  </div>
</div>
</body>
</html>
Explanation of Example 2:
  • Every visible element has a light class and a dark: twin — page, card, text, border, even the button's base and hover colors.
  • With v4's default strategy there's nothing else to set up: dark: tracks prefers-color-scheme, so the OS toggle repaints the page live.
  • Notice dark mode isn't "white text on black" — it's a re-tuned palette: surfaces step down (white → gray-900 → gray-950), muted text steps up (gray-600 → gray-400), and accents get lighter (blue-600 → blue-500) for contrast.
  • For an in-page toggle button instead, add the @custom-variant dark line from Section 2 and flip the dark class on <html> with a line of JS.
How to run
Save as index.html and open in a browser with internet. Switch your OS/browser to dark mode and back — no reload needed. To make it class-based (for a manual toggle), add @custom-variant dark (&:where(.dark, .dark *)); to a small <style> tag and toggle the dark class on document.documentElement.

5Advantages

  • Behavior without CSS: hover/focus/active effects are class lists, not selectors — no &:hover nesting, no stylesheet round-trips, and deleting the element deletes its behavior.
  • Consistent state vocabulary: everyone uses the same variants, so interactive elements feel identical across a whole product.
  • group-hover unlocks real component interactions: card hovers, arrow slides, revealed actions — the classic parent-hover-styled-child pattern without any descendant selectors.
  • Accessibility is one class away: focus-visible:ring-2 gives keyboard users what hover gives the mouse; disabled: handles dead states; dark: follows the user's system preference for free.
  • Composes with everything: state variants stack with responsive prefixes (md:hover:bg-blue-800), opacity (bg-blue-500/50), and transforms — the whole system is one syntax.
  • A mature ecosystem around it: @tailwindcss/typography handles long-form content with prose, and Headless UI supplies the accessible interactive primitives (dialog, menu, combobox…) that you skin with exactly these variants.

6Conclusion

State variants are Tailwind's answer to "when should this look different?": hover: (pointer over), focus:/focus-visible: (keyboard and click focus), active: (pressed), group-hover: (a group-marked parent is hovered), and dark: (dark mode). The syntax is always variants first, utility last, they stack with each other and with responsive prefixes, and paired with transition they give every element polished, accessible interactivity without a single line of hand-written CSS.

And the ecosystem completes the picture: @tailwindcss/typography styles whole articles with one prose class, while Headless UI provides the keyboard-perfect interactive components that you style with the very variants on this page. Behavior from Headless, words from prose, everything else from utilities — that's the full Tailwind toolbox.
