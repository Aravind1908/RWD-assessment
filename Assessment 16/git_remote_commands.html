Git: Remote Repository Commands

clone, remote, push, pull, fetch — how local work meets shared work — plus the one distinction that matters most: pull vs fetch.

Version Control · Git · Collaboration

1Introduction

Everything so far has been on one machine. Collaboration needs a second copy of the repository that others can reach — a remote repository. A remote is just another clone (usually on GitHub/GitLab, but it could be a USB stick): your machine and the remote exchange commits with push (send) and fetch/pull (receive).

The five verbs, in one line each:

CommandIn one line
git clone <url>download a complete copy of a remote repo (history included) and set up origin
git remotelist and manage your named remotes
git pushupload your local commits to a remote branch
git fetchdownload the remote's new commits — without touching your work
git pullfetch and immediately merge into your current branch
your machine                          remote ("origin")
main ────────●──●──●─── push ──────>  main ──────●──●
   ▲                                    │
   └────────── fetch / pull ◀───────────┘

One key piece of machinery makes the rest click: for every branch on a remote, Git keeps a remote-tracking branch — origin/main — a local mirror of where the remote's branch currently is. fetch updates that mirror; it never updates your branch.

2Syntax and its Explanation

git clone — the door in

git clone https://github.com/team/site.git   # folder "site" appears
git clone https://github.com/team/site.git my-folder  # choose the name

One command that does three things: downloads the entire repository (full history, all branches), creates the working folder, and registers the source URL as the remote origin. Because it's a full copy (distributed model), you can work offline immediately and the clone doubles as a backup.

git remote — named pointers to other repos

git remote               # list names: origin, …
git remote -v            # names + their URLs (fetch and push)
git remote add fork https://github.com/me/site.git
git remote remove fork

A remote is just a name bound to a URL. Projects often have more than one — origin plus a personal fork, a backup mirror, a second server. Your remote-tracking branches are named after them: origin/main, fork/main.

git push — upload your commits

git push origin main       # upload local main to origin/main
git push -u origin main    # -u sets "upstream": bare push/pull work from now on
git push origin main:fixes # push to a differently-named remote branch

Push is one-directional and honest: it uploads the commits on your local branch to the named remote branch, and refuses if someone else's new commits would be overwritten (a "non-fast-forward") — you must integrate first. -u (set upstream) is a one-time convenience; after it, git push alone knows where to go.

git fetch — download, don't integrate

git fetch                # update origin/* mirrors for the current remote
git fetch origin main    # just one branch
git fetch --all          # every remote
git fetch --prune        # also drop remote branches that were deleted

Fetch is the read-only command. It downloads new commits and refs and moves the remote-tracking branches (origin/main advances). Your local branch, your index and your working directory are completely untouched — which is exactly why it's safe to run at any time, on any branch, even mid-work.

git pull — fetch + merge in one step

git pull                 # = git fetch + git merge origin/<current branch>
git pull --rebase        # fetch + rebase your commits on top (linear history)

Pull is fetch followed immediately by a merge of the downloaded commits into your current branch. Same information as fetch — plus it changes your branch, can create a merge commit, and can create merge conflicts. It's the fast path; fetch is the careful path.

pull vs fetch — the difference that matters

git fetchgit pull
Downloads the remote's new commitsyesyes
Updates origin/main (the remote-tracking branch)yesyes
Updates your branch / working directorynoyes (merge or rebase)
Can create merge conflictsnoyes
Safe to run anytimeyes — it's read-onlyonly when you're ready to integrate
Afterwards you can…inspect main..origin/main, then merge/rebase when you chooseit's already merged (or you're resolving conflicts)

One sentence: fetch is "show me what changed on the remote"; pull is "fetch, and bring it into my branch right now".

The safe loop, as a habit: git fetch → look (git log --oneline main..origin/main and git diff main origin/main) → integrate when ready (git merge origin/main or git rebase). Teams that fetch before they merge have far fewer surprise conflicts at the end of the day.

If you remember one thing: pull = fetch + merge. Fetch is the harmless half of pull — so reaching for fetch first costs nothing and removes most "why did my pull just change everything?" moments.

4Example Programs with Explanation

Both scripts simulate a team on one machine: a bare Git repository plays the shared "origin", and two clones are two people's laptops. Everything is built in a temp folder and cleaned up afterwards.

Example 1 — clone, remote and push: getting started and sharing

One bare repo, two clones. Machine A pushes; machine B — which only existed a moment ago — already has the full history.

#!/usr/bin/env bash
set -euo pipefail
root=$(mktemp -d) && cd "$root"

# a bare repository plays the shared remote "origin"
git init -q --bare --initial-branch=main origin.git

# clone it — one command: full repo + folder + 'origin' configured
git clone -q origin.git site
cd site
git config user.email "[email protected]"
git config user.name  "You"

git remote               # origin — created automatically by clone
git remote -v            # the URL it points to

echo "hello" > index.html
git add index.html
git commit -qm "first page"
git push -u origin main  # -u: origin/main becomes my upstream

# a second machine clones the same remote…
cd "$root"
git clone -q origin.git backup
cd backup
git log --oneline        # …and already has machine A's commit
git ls-files             # …and its files too
Explanation of Example 1:
  • clone did three jobs in one step: downloaded the complete repository, created the site folder, and registered origin — which is why git remote already lists it.
  • git remote -v shows what a remote is: a name bound to a URL, used for both fetch and push.
  • push -u uploaded the commit and recorded "upstream": from now on, bare git push/git pull know which remote branch to talk to.
  • The backup clone appeared seconds later and contains the commit — because cloning a remote copies the whole history, not a working snapshot.
How to run
Save as example1_git_remote_clone_push.sh and run bash example1_git_remote_clone_push.sh. Only Git is needed; a temp folder is created and used.

Example 2 — pull vs fetch, shown on the same branch

Machine A starts the project; machine B joins and works in parallel — its clone already contains A's base commit. While B pushes, you run the safe loop: fetch, inspect, integrate on your own schedule, and see exactly what pull would have done in one step.

#!/usr/bin/env bash
set -euo pipefail
root=$(mktemp -d) && cd "$root"

# a bare repository plays the shared remote "origin"
git init -q --bare --initial-branch=main origin.git

# machine A joins first: clone, first commit, push
git clone -q origin.git me
cd me
git config user.email "[email protected]"
git config user.name  "You"
echo "shared base" > notes.txt
git add notes.txt
git commit -qm "base"
git push -q origin main

# machine B joins next — its clone already contains "base"
cd "$root"
git clone -q origin.git teammate
cd teammate
git config user.email "[email protected]"
git config user.name  "You"

# the teammate pushes a new commit while I'm working
echo "teammate's line" >> notes.txt
git commit -qam "teammate: update notes"
git push -q origin main

# me: the safe loop — fetch, inspect, integrate when ready
cd "$root"/me
echo "my line" > my-file.txt
git add my-file.txt
git commit -qm "me: add my file"

git fetch                          # 1) download — my branch is untouched
git log --oneline main..origin/main # 2) what I'm missing
git diff main origin/main --stat    #    …and what it changes
git merge origin/main              # 3) integrate — `git pull` is 1+3 in one go
git log --oneline --graph
git push                           # now my branch is ahead — upload it
Explanation of Example 2:
  • After git fetch, run git log --oneline yourself: your branch still has only "base" + "me" — fetch moved origin/main, not main.
  • git log main..origin/main lists exactly the commits you're missing; git diff main origin/main shows the changes they'd bring in. This is the "peek before you merge" that raw pull skips.
  • git merge origin/main integrates on your schedule — git pull would have performed steps 1 and 3 together, immediately, no inspection in between.
  • The final git push uploads your branch (now containing everyone's work). Notice push never had to guess anything: your branch was ahead, so it was a clean fast-forward.
How to run
Save as example2_git_fetch_vs_pull.sh and run bash example2_git_fetch_vs_pull.sh. Watch the --graph log at the end: two lines of work woven into one.

5Advantages

  • clone is a complete onboarding: full history, working files and configured remote in one command — and every clone is a backup by construction.
  • Remotes are cheap named pointers: origin, forks, mirrors and backups can all coexist; switching or adding one is a one-line change, not a re-setup.
  • Push is honest and safe: it uploads your commits and refuses to overwrite others' — conflicts are caught at the boundary, not hidden in someone else's day.
  • Fetch is a zero-risk peek: read-only, anytime, any branch — the habit that turns "surprise merge conflict" into "planned integration".
  • Pull keeps the fast path simple: one word when you know the remote is safe to integrate.
  • Remote-tracking branches are always-current mirrors: origin/main tells you what the remote thinks, independently of what your branch does.

6Conclusion

Collaboration in Git is five verbs around a model: clone brings you a complete copy with origin already wired up; remote manages the named connections; push uploads your commits; fetch downloads the world's new commits into origin/* mirrors without touching you; and pull is simply fetch + merge — the same information, but applied to your branch immediately.

The daily loop that follows from that model: fetch (or pull) in the morning, commit and push in the evening. Remotes are mirrors, not masters — and the fetch-first habit is the difference between a smooth day and a merge-conflict afternoon.
