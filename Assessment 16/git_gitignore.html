What is .gitignore?

A small file with a big job: telling Git which files are not part of the project. Why it matters — size, secrets, noise — the pattern syntax, and the examples that belong in every repo.

Version Control · Git · .gitignore

1Introduction

A repository should contain exactly the files the project needs — and not one more. .gitignore is a plain-text file, usually at the repository root, that lists patterns of files Git should not track. Ignored files stay on your disk, working as normal — they simply never enter git status, never get committed, and never get pushed.

It looks like a list of file names because it is: 

# node_modules/ — hundreds of MB, rebuilt by `npm install`
node_modules/
# build output — machine-generated, different on every machine
dist/
# secrets — must never exist in history
.env

Its importance isn't cosmetic. Without it, a repository accumulates three kinds of damage that compound forever:

  • Bloat — dependency folders and build artifacts make clones slow and storage expensive, on every machine, forever.
  • Leaks — .env files with API keys, database passwords and private keys get committed, and a secret in Git history is a secret that was always exposed (even after the file is deleted, it lives in old commits).
  • Noise — logs, caches and OS files make git status a wall of unrelated changes, so the real change hides.

2Syntax and its Explanation

The pattern language

# blank lines and # comments are ignored
*.log              # any .log file, at any depth
build/             # a directory named build (trailing / = directories only)
/temp              # leading / anchors to THIS .gitignore's folder
**/tmp             # a tmp directory/file at any depth
docs/*             # everything in docs/…
!docs/keep.md      # …except keep.md (negation)
PatternMeaning
namea file (or directory) with that name, at any level
dir/directories only (trailing slash)
/nameonly at the location of this .gitignore (root, if it's the root one)
*any characters except /
**any depth of folders
!namere-include a file a previous pattern ignored

Patterns are matched against paths relative to the .gitignore file that contains them, and later lines win — which is how docs/* + !docs/keep.md ignores a folder but rescues one file.

Where ignore rules can live

LocationScopeShared?
.gitignore at repo rootthis project, whole treeyes — committed with the code
.gitignore in a subfolderpatterns relative to that subfolderyes
git config --global core.excludesFile ~/.ignore_globalevery project on your machineno — personal
.git/info/excludethis clone onlyno

The split to internalize: project rules in the committed .gitignore; personal rules (your editor's files) in the global excludes file.

The trap: ignoring ≠ untracking

.gitignore only affects files Git has never tracked. If .env was already committed, adding it to .gitignore changes nothing — Git keeps tracking it and the ignore line is silently useless. The fix is two steps: git rm --cached .env (remove from the index, keep on disk) and then commit. Example 2 walks through exactly this.

3Features & Uses

What belongs in .gitignore — and why

CategoryTypical patternsWhy
Secrets & environment.env, .env.local, *.pem, secrets.json, id_rsacredentials must never exist in history — once pushed, assume exposed
Dependenciesnode_modules/, venv/, .venv/, vendor/huge and regenerable: npm install / pip install -r requirements.txt
Build outputdist/, build/, target/, out/, __pycache__/, *.pyc, *.classmachine-generated; differs per build and per OS
Logs & temp*.log, logs/, tmp/, *.tmpchurn constantly; add noise, carry no source
OS & editor cruft.DS_Store, Thumbs.db, *.swp, .idea/, .vscode/personal to each machine/user — global excludes are often better

Debugging: why is this (not) ignored?

git check-ignore -v node_modules/express   # → .gitignore:2:node_modules/  node_modules/express

git check-ignore -v answers "which rule matches this path?" — the first-line answer to every "wait, why is Git tracking that?" moment. Exit code 0 = ignored, 1 = not.

Ignore categories, not files. *.log covers the log you haven't created yet; node_modules/ covers every dependency you'll ever add. A .gitignore that lists individual files will be outdated the day after it's written.
If a secret ever gets committed: 1) rotate the credential now (it's in history — deleting the file doesn't un-expose it), 2) git rm --cached .env + commit so it's no longer tracked, 3) if it was pushed, rewrite history (git filter-repo / BFG) and force-push, or accept the rotation as the real fix.

4Example Programs with Explanation

Both scripts build a throwaway repo in a temp folder, print git status at each step, and clean up after themselves.

Example 1 — Watch .gitignore work: from noise to signal

A realistic young project: source code, a dependency folder, a secret and a log. First status without the ignore file, then with it.

#!/usr/bin/env bash
set -euo pipefail
demo=$(mktemp -d)/ignore-demo && mkdir -p "$demo" && cd "$demo"
git init -q --initial-branch=main
git config user.email "you@example.com"
git config user.name  "You"

# a typical young project
mkdir -p src node_modules
echo "app code" > src/app.js
echo "packages…" > node_modules/some-dep.js
echo "API_KEY=super-secret" > .env
echo "request log" > server.log

echo "== before .gitignore: status is full of noise =="
git status --short

echo "== write .gitignore =="
cat > .gitignore <<'EOF'
# dependencies — regenerated by `npm install`
node_modules/
# secrets — never commit
.env
# logs
*.log
EOF
git add .gitignore
echo "== after: only the real project remains =="
git status --short
git check-ignore -v node_modules/some-dep.js .env server.log

git add -A
git commit -qm "first commit"
git ls-files                    # what actually entered the repository
Explanation of Example 1:
  • Before the file, git status --short lists everything — .env, node_modules/, server.log — as candidates for commit.
  • After it, the same status shows only src/ (and the newly added .gitignore) — the ignore file didn't delete anything, it just told Git to stop seeing those paths.
  • git check-ignore -v prints the exact line that matched each path — proof of which rule did the work.
  • git ls-files at the end is the final answer to "what's in the repo": .gitignore and src/app.js. The secret, the packages and the log live on disk only.
How to run
Save as example1_gitignore_basic.sh and run bash example1_gitignore_basic.sh. The before/after status output is the whole lesson.

Example 2 — The classic trap: already-tracked files can't be ignored

A secret was committed before anyone wrote a .gitignore. Adding the ignore line does nothing — watch why, and the fix.

#!/usr/bin/env bash
set -euo pipefail
demo=$(mktemp -d)/tracked-demo && mkdir -p "$demo" && cd "$demo"
git init -q --initial-branch=main
git config user.email "you@example.com"
git config user.name  "You"

# oops: the secret was committed before any .gitignore existed
echo "API_KEY=super-secret" > .env
git add -A
git commit -qm "first commit (with the secret)"
git ls-files                     # .env is tracked

echo "== adding .gitignore now does NOT untrack it =="
cat > .gitignore <<'EOF'
.env
EOF
git add .gitignore
git commit -qm "add .gitignore"
git ls-files                     # .env is STILL listed — ignore ≠ untrack
git status --short               # clean, because Git still tracks .env normally

echo "== the fix: remove from the index, keep it on disk =="
git rm --cached .env
git status --short               # staged deletion of .env (file still on disk)
git commit -qm "stop tracking .env"
git ls-files                     # .env no longer in the repository
ls                               # …but the file itself is still right here
echo "remember: the secret still lives in old commits — rotate it"
Explanation of Example 2:
  • After .env is tracked, a new .gitignore line is silently useless — git ls-files proves the file is still tracked, and status stays clean because Git considers it "normal".
  • git rm --cached .env is the untracking move: it removes the file from the index (and thus from future snapshots) while leaving the file on your disk, untouched.
  • After the deletion commit, ls-files no longer lists .env and ls still shows it — ignored, local, safe from future commits.
  • The final line is the part people forget: old commits still contain the secret. Untracking stops future exposure; rotating the credential is what fixes the past one.
How to run
Save as example2_gitignore_already_tracked.sh and run bash example2_gitignore_already_tracked.sh. The two ls-files outputs — identical, then different — are the trap and the fix.

5Advantages

  • Small, fast repos: no node_modules/, no build output — clones stay small and storage stays cheap, for every contributor, forever.
  • Secrets stay out of history: the cheapest line of defense against credential leaks — and it's the one teams often discover too late.
  • Clean git status: logs, caches and OS files stop churning, so the output shows only real project changes.
  • Deterministic builds: everyone builds from source, not from build artifacts generated on someone else's machine with someone else's toolchain.
  • Right scope for every rule: project rules in the committed .gitignore, personal rules in the global excludes file — team and machine stay separate.
  • Debuggable: git check-ignore -v shows exactly which rule matched — no guessing.

6Conclusion

.gitignore is a promise in file-list form: these paths are not part of the project. Its pattern language is small — wildcards, trailing slashes, a leading anchor, and ! to rescue exceptions — and it's where the repo draws its boundary between source of truth (committed) and machine-local noise (ignored).

Two habits carry it: ignore categories, not individual files, and remember that .gitignore never untracks anything — already-committed files need git rm --cached, and leaked secrets need rotation before any history cleanup. A repository that respects its own .gitignore stays small, honest and fast — on every machine that ever clones it.
